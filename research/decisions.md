# Decisions

- D-001: Python 3.11+, stdlib `sqlite3` + FTS5, `tomllib`; psutil is the only runtime dependency so far.
- D-002: `EchoModel` stub backend so everything is testable without weights. `llama_cpp` backend is implemented but untested here (no weights/library in the sandbox).
- D-003: Language model is declared `resident` in the router (loaded once by the app).
- D-004: Exact arithmetic uses `Fraction` with an AST whitelist (no `eval`), caps result size, and refuses irrational sqrt rather than returning floats.
- D-005: Conflicts never delete history. Superseded by D-033: stronger evidence may de-index older records only under an explicit verification policy; weaker evidence is stored but not searchable.
- D-006: AMA runs synchronously after the answer for now; async/background deferred.
- D-007: AMA weights, NFD weights and thresholds stay at uncalibrated defaults and are labelled as such.
- D-008: Adaptive memory implemented in NumPy (analytic gradient of a linear memory); PyTorch was not installable in the dev sandbox. Port to PyTorch (safetensors checkpoints) when the memory becomes non-linear or on the target laptop.
- D-009: Adaptive memory stays OUT of the controller's response path until it shows an advantage over FTS5. It is fed only through AMA's `neural_memory` queue via `drain_neural_queue`.
- D-010: Hyper-parameters (lr) are tuned on a separate validation seed, never on the reported seeds.
- D-011: Ollama is a supported foundation backend (stdlib HTTP only). Pinning is by Ollama digest instead of GGUF sha256; a mismatch refuses to run. Greedy decoding (temperature 0, seed 0) for reproducibility.
- D-012: Server-side memory is read from `ollama ps`, never from this Python process's RSS (the model lives in the Ollama server).
- D-013: A model is only called better/worse than the reference if a two-sided exact sign test on paired strict results gives p < 0.05. Small differences are reported as "no detectable difference".
- D-014: Deletion integrity is enforced by SQL triggers (not only Python), so it cannot be bypassed by a future code path. admission_log is an audit trail and survives deletion.
- D-015: Forgetting never touches verified/corrected/trusted records, conflict evidence, reinforced records or queued items.
- D-016: The AMA answer comparator errs toward "conflict" when unsure (stored as evidence, not indexed) rather than toward silently merging two answers that might disagree.
- D-017: Phase 0 foundation is `qwen3.5:2b` (Qwen3.5 1.9B, Q8_0, Apache-2.0, digest 0689d44085e0). It fits the 2 GB VRAM budget at 2.3 GB and measured 0.56 strict / 4.5 s p50 on `baseline_v2` (EXP-000c). The 7B Qwen2 fine-tune scored 0.94 but took 50.7 s p50 and is not viable as the live model (F-014). Thinking is disabled on the fast path (`think=false`).
- D-018: DPF fast state wraps the existing adaptive memory and is bounded by `FastConfig.max_delta_norm`; slow state is a file-based `CheckpointStore` whose `promote()` requires a passing `NGRResult`. DREAM trains the same small NumPy memory, never the language model, and held-out examples are isolated from training (adding a duplicate across splits raises).
- D-019: BrainSim is an independent subproject under `BrainSim/` with its own package, tests, checkpoints and research record. ASHURA does not import it and the ASHURA test suite is unchanged. Integration starts only after BrainSim demonstrates useful learning independently (v2 blueprint section 21); the narrow B1/fast-memory milestone does not yet justify wiring it into the response path.
- D-020: BrainSim fast memory is task-scoped and reset at episode boundaries. In BS-EXP-001, leaving memory active across a task switch dropped old-rule accuracy by 64.8 points (token keys) or 5.3 points (pair keys), both above the 2% tolerance; after reset the old-rule accuracy was exactly restored. Cross-task memory needs a gate before any integration. See `BrainSim/research/failures.md` F-BS-001/F-BS-002.

- D-021: OCR is an optional local skill (`skills/perception/ocr.py`) with Pillow + pytesseract and a local Tesseract executable. The registry marks it available only when the engine can actually run; otherwise NFD reports it as unavailable rather than silently pretending. OCR output is stored as unverified, with image hash, confidence and engine version; corrections are explicit and separate. No OCR accuracy is claimed until a held-out target corpus is measured.
- D-022: The HARN addition candidate is non-authoritative. `skills/arithmetic/exact.py` always computes the answer; the candidate is logged as agreeing/rejected and can never replace or veto it. The current candidate is linear least-squares, not a deep network, and its 1.000 held-out match is expected on a linear task. HARN success is not claimed.
- D-023: BrainSim B2 is a capability baseline, not evidence for recurrence. The GRU solved delayed recall at every delay, but a parameter-matched fixed MLP also reached 1.000 and trained 6-16x faster. H-DELAY is falsified; the task saturates and the delay carries no task-relevant information. Do not cite B2 as a recurrent advantage.
- D-024: BrainSim B3 uses task-scoped memory with an externally supplied task ID and verified writes. It retains old-task accuracy at 1.000 versus 0.104 for shared memory, but does not test learned task identification or surprise-gated admission. Task-scoped reset remains the safe default; integration stays deferred.
- D-025: D-017 is superseded. The live foundation is `tony:7b` (Qwen2 7.6B, Q4_K_M local fine-tune, digest 0455603ff430). It measured 0.94 strict / 2.35 s p50 on `baseline_v2` versus 0.56 / 3.9 s for `qwen3.5:2b` (EXP-000d). The accuracy gap is not significant on 16 items (8 discordant pairs, p=0.07), so adoption rests on the measured latency and the user's confirmed real-world use, not a proven accuracy win. Its 4.6 GB footprint exceeds the 2 GB VRAM budget (shared memory), so `qwen3.5:2b` (2.3 GB) remains the documented fallback. `config/module_costs.json` is recalibrated from the tony:7b row.
- D-026 (Phase 1, P03/P04): Verification is three-state (`VERIFIED`, `FAILED`, `UNAVAILABLE`), not `bool | None`. Only `VERIFIED` may produce verified admission, semantic facts or a DREAM label. `Response.verified` keeps the legacy True/False/None view; `Response.verification` and `TraceStep.verification` carry the factual state, while `TraceStep.ok` means the verifier executed. An unavailable verifier is never counted as factual success.
- D-027 (Phase 1, P01/P02): Retrieval is reliability-aware. The default cutoff is 0.5, so unverified model output (0.2) is not retrieved as evidence. Every returned item carries source, verification method, timestamp, reliability and conflict status; the prompt labels verified, trusted, user-provided and unverified material. Semantic facts require `verification_status="verified"`, not merely a high reliability score.
- D-028 (Phase 1, P05/P06): A user correction is stored as a separate immutable `user_provided` record (`output=""`, `source="user"`) at reliability 0.6. The assistant's generated reply is never relabelled `user_corrected`. User material is a record of what the user said, not independent proof; it cannot enter semantic/DREAM queues or override verified or trusted evidence. The full verified-correction path remains Phase 3.
- D-029 (Phase 1, P09-P11): NGR rejects NaN, +/-infinity, out-of-range scores, missing required capabilities and invalid sample counts. `NGRPolicy(require_performance=True)` requires p95 latency and peak RAM, and missing measurements reject promotion. Metric direction, range, minimum samples and epsilon are defined per capability in `MetricSpec`. The strict requirements are opt-in so existing experiments remain reproducible; the production promotion path should enable them once real measurements exist.
- D-030 (Phase 1, P12-P14): DREAM measures four arms (stable/fresh x new/replay) and can initialize a candidate from the stable memory. The answer vocabulary is fixed from training data or an explicit task specification, never held-out answers. A missing stable checkpoint is not replaced by zero scores: a separately evaluated baseline artifact and a `cold_start_min_target_accuracy` criterion are required for first promotion. In EXP-006, stable+new and stable+replay both retained old capability at 1.00; fresh+new was rejected at 0.00 retention; this is a pipeline result, not a general replay claim.
- D-031 (Phase 2, P15-P17): AMA admission is one transaction and uses cached tokenisation. On EXP-001 it measures 1.40 ms/item vs 1.13 ms for store-everything (1.24x, previously ~6x). The remaining ~27% database growth is audit (`admission_log`), semantic facts and conflict evidence, not accidental duplication; semantic fact text is deduplicated against its source episode. The discard threshold stays 0.45 because 1.6 (best synthetic F1) discards all novel unverified records needed for audit.
- D-032 (Phase 2, P18): Utility is measured from later feedback events (retrieval hit, acceptance/rejection, task completion, correction) in `memory_feedback`. It changes usefulness ranking only and never changes reliability or verification status. Retrieval-hit logging is opt-in so the read path does not become a write path.
- D-033 (Phase 2, P21): Conflicts live in a dedicated `conflicts` table with question, both evidence classes, reliability snapshots, policy and resolution. A claim supersedes only when it is independently verified and strictly stronger than every old claim; two verified claims remain open. Resolution requires an explicit explanation, and supersession requires a verified experience. Reliability alone never resolves a conflict.
- D-034 (Phase 2, P19/P20/P26): Answer comparison is rule-based: value extraction (numbers, dates, identifiers), unit normalisation, scoped negation and continuous similarity. On a 28-pair author-written benchmark it scores 1.00 accuracy vs 0.64 for the lexical comparator and Brier 0.013 vs 0.381. This is not semantic understanding; unknown paraphrases remain conflicts for review. No local encoder is adopted without a held-out win.
- D-035 (Phase 2, P22/P24/P25): FTS5 remains the memory default. IDF is essential for the adaptive memory (0.997 vs 0.010 exact), but the adaptive memory loses to FTS5 under noise (0.41 at 10 distractors), capacity (0.88 related at 400 facts) and task switches (0.84 -> 0.04). It stays experimental and out of the response path (D-009).
- D-036 (Phase 2, P23): Neural-memory writes are gated on independently verified status, a reliability floor, absence of an unresolved verified/trusted conflict, bounded passes and a hard per-drain cap. The drain snapshots the learned state before writing and restores it on failure, so old associations remain recoverable. Rejected queue items are removed and logged as `NEURAL_UPDATE_REJECTED`.
- D-037 (Phase 2, P27): Retention uses utility/retrieval frequency as a protection signal and never forgets verified/trusted/user records, recently used records, reinforced records, conflict evidence or queued items. The benchmark forgot 100/100 intended records with 0 protected records lost and 0 stale index/fact rows.
- D-038 (Phase 2, P28/P29): Replay ratio and sampling policy remain uncalibrated (all arms tie at 1.00 on the synthetic task); the default stays 0.5 with no calibration claim. Semantic facts require a verified source episode and store provenance JSON, verification method, derivation and source id; deleting the source removes the fact.
- D-039 (Phase 3, P05/P06/P07): A correction is parsed and classified before any learning. Exact arithmetic equations (`+ - * /` at introduction; extended by D-042) are checked by Fraction evaluation plus a Decimal(60) cross-check and may produce a second, verified training record; false equations and factual claims remain `user_provided`. The user's original sentence is always stored separately and the assistant reply is never relabelled.
- D-040 (Phase 3, P07/P75): The verified-correction loop is an explicit chain (`learning/loop.py`): verified correction -> CAGE attribution -> authorisation -> bounded proposal -> temporary fast update -> DREAM candidate -> NGR -> promotion/rollback. Each stage can refuse with a reason. It is not automatically invoked by the live controller yet, because the previous execution trace is not retained.
- D-041 (Phase 3, A01-A03): Fast plasticity and slow consolidation remain separate. `FastWeights` measures immediate adaptation; `CheckpointStore` changes only when NGR promotes a candidate. A rejected candidate leaves the stable pointer unchanged. The candidate is the NumPy adaptive memory, not the language model (D-009 stands).
- D-042 (Phase 3, P47/F-006/F-042): The independent Decimal(60) backend now cross-checks `%` (floor semantics), integer `**` and perfect-square `sqrt`, so those exact results can become verified. Irrational roots, non-integer exponents and comparisons remain unavailable; the exact path never fabricates a value. Tolerance stays relative 1e-40. An expression whose Decimal operation needs more than the 60-digit context (for example a modulo with a >60-digit quotient) is reported unavailable, not verified.
- D-043 (Phase 3, F-041): The controller retains the last non-correction `ExecutionTrace` and accepts an optional `correction_loop` hook. A verified correction invokes the hook against that trace; a hook error is recorded in `Response.correction`, never raised into the answer path. The CLI does not configure a loop because no replay corpus or stable checkpoint is defined for live use.
- D-044 (Phase 3, F-044): EXP-013 is run over five seeds and reports promotion counts, not a single showcase run. A seed whose stable baseline accidentally matches the corrected held-out items is reported as a rejection, not tuned away. The two-item corrected held-out set is a known measurement weakness.
- D-045 (Phase 2/3, F-039): Conflict review is a minimal CLI (`learning/review.py list|resolve`). Superseding still requires an independently verified experience; dismissal records an explicit reason. No UI, notification or queue prioritisation is claimed.
- D-046 (Phase 3/5, F-042/F-043): Any future language-model lane uses the pinned local foundation `tony:7b` (D-025), not a new Qwen model; `qwen3.5:2b` remains only the documented fallback. No external LLM APIs. A language model may generate candidate text, but it may not independently verify its own claim: F-042 stays open until a trusted local source or a genuinely independent verifier exists.
- D-047 (Phase 3, P67/F-041): Background learning is opt-in and isolated in `learning/worker.py`. `LearningWorker` uses one daemon thread and a bounded queue; `submit()` never raises, queued jobs can be cancelled, running jobs are not force-killed, and `stop()` drains queued work. The controller may use the worker as its `correction_loop` and records the returned `job_id`. Jobs are in-process only: no durable queue, restart recovery or hard timeout for a running job is claimed. (Superseded for durability by D-058.)
- D-048 (Phase 3, F-044): EXP-014 is the larger frozen correction benchmark: 10 author-written arithmetic forms, 3 held-out wordings each, 5 seeds, replay/no-replay arms and 5 control probes. It reports 50/50 replay promotions, 0/50 no-replay promotions, 150/150 held-out wording predictions and 25/25 refused controls. The result is not tuned after inspection and does not close F-044: the corpus is not independently authored and the held-out wordings share expression tokens with the correction key.
- D-049 (Phase 3, P61-P63/P69): EXP-015 records measured single-process costs on the target laptop: exact arithmetic p50 <= 0.015 ms, AMA admission p50 1.35 ms, FTS5 search p50 0.29 ms, full NumPy loop p50 24.4 ms, and a 300-turn EchoModel mix at p50 1.39 ms / p95 1.78 ms with ~1 MB RSS and 0 errors. These are not `tony:7b` measurements and must not replace the language cost row or routing estimates without a separate routing experiment.
- D-050 (Phase 3, F-046): EXP-015's optional cold-start `tony:7b` mixed load (24 free-form general turns + 8 exact arithmetic turns, pinned digest `0455603ff430`) measured language p50 5.52 s / p95 8.06 s, 7.4 generated tokens/s, 0 errors, a 4,635.9 MB Ollama-reported model footprint and ~97 MB ASHURA client RSS; arithmetic stayed at p50 2.42 ms because it bypasses the model. This is one short single-process run, not a production soak: it does not establish concurrency safety, model reload, restart recovery or routing, and its free-form answers are longer than EXP-000d's short-answer baseline. Keep the `config/module_costs.json` language row unchanged.
- D-051 (Phase 3, F-046/F-047): EXP-016 closes F-046 only for the bounded scope: 4 concurrent client processes, 80 mixed turns, 0 failures; one forced unload/reload (22.41 s wall / 9.11 s Ollama load); and a fresh-process restart that found both a verified arithmetic record and a user-provided memory record (write PID 1552, verify PID 12164). The same run rejects a parallel-throughput claim: general p50 rose from 5.52 s single-client to 25.80 s under four clients (~4.7x) with ~0.31 server CPU utilisation. F-047 remains open for queueing/parallel inference. F-045 remains separate for durable worker jobs. (F-047 is superseded for its bounded scope by D-059; F-045 by D-058.)
- D-052 (project evidence): ASHURA's listed capabilities are requirements, not demonstrated capabilities. SQLite memory, `FastWeights`, DREAM, persistent neural parameters and `tony:7b` weights are separate mechanisms. The current evidence supports memory/retrieval and a bounded NumPy candidate loop, not a language-model capability change. Future capability claims must use the four tests (remember, generalise, consolidate, retain) and the standard experiment record in `research/evidence_standard.md`; negative results are retained.
- D-053 (Phase 3, A02/A03): EXP-017 demonstrates consolidation persistence for the NumPy candidate: 20/20 promoted candidates were loaded by a fresh process with matching artifact SHA-256, 60/60 corrected held-out predictions and 400/400 old-capability predictions survived the restart, and 20/20 rollbacks restored the parent checkpoint. This is bounded evidence for the NumPy adaptive memory, not for `tony:7b`; no language-model weight, adapter or LoRA was trained. F-043 remains open. The completion audit (`research/completion_audit.md`) scores the engineering checklist separately from the central language-learning claim.
- D-054 (Phase 0/F-043): The user-supplied fine-tune is the local tag `tony:7b-gpa3` (digest `2a86766287cf`), not `tony:7b_gpa3`. Treat it as an evaluation candidate, keep `tony:7b` (digest `0455603ff430`) as the prior reference, and keep `qwen3.5:2b` as the documented fallback. Do not change the configured model until a frozen benchmark and retention checks pass.
- D-055 (Phase 0/F-043): F-043 is re-scoped from "no language-model fine-tune exists" to "a user fine-tune exists but was unverified, unevaluated and not integrated." Its claims require a digest, licence, dataset provenance, held-out evaluation and regression evidence. The user reports that gpa3 was already compared favourably with Qwen2.5-7B-Instruct in prior versions; that comparison is recorded as user-reported, not independently reproduced here, because no base checkpoint was downloaded.
- D-056 (Phase 0/EXP-018): Adopt `tony:7b-gpa3` as the general tutor default and keep `tony:7b` as the privacy profile. EXP-018 tied both at 41/42 adjudicated answers on a frozen 42-item subject suite; gpa3 was faster (1.86 s vs 3.04 s p50) and more concise, while tony:7b was more explanatory. The base-model comparison and privacy preservation were not measured by ASHURA. This does not change the central language-learning claim: ASHURA still demonstrates 0 of 4 language-model learning tests because it trains neither checkpoint.
- D-057 (Phase 0/EXP-018b): `tony:7b-agentic3` (digest `0efe3817d5c1`) ties gpa3 and tony:7b at 41/42 adjudicated on the same frozen subject suite, but has lower format compliance (0.881 vs 0.976), higher p50 (2.11 s vs 1.86 s), and a transient 154.7 s outlier. It does not replace gpa3 as the general tutor. Keep it as a candidate for a separate agentic/tool-use benchmark; the subject suite does not measure tool use, planning or multi-step agency.
- D-058 (F-045): Background learning jobs can now be persisted in a local SQLite `learning_jobs` table, recovered after a restart (queued jobs re-scheduled; running jobs marked interrupted), and run under an optional hard timeout in a spawned child process that is terminated at the deadline. The opt-in CLI wiring requires `learning.enabled = true`, a JSONL replay corpus and a checkpoint directory; it is disabled by default. Residual limits: one worker per store; recovery is at-least-once for queued jobs; hard-timeout mode requires a picklable runner; the CLI path has configuration tests but no live real-model learning run. F-045 is fixed for this bounded scope, not for production multi-worker scheduling.
- D-059 (F-047/EXP-019): Concurrent inference is now explicitly bounded. The client gate (`max_inflight=1`, `max_queue=8`, `queue_timeout_s=60` in the shipped Ollama profiles) prevents one ASHURA process from growing an unbounded queue; the Ollama server owns the real parallel slots. EXP-019 measured `OLLAMA_NUM_PARALLEL` 1/2/4 with 1/2/4 clients: one slot serializes (4.93 to 5.95 tokens/s, p50 6.57 to 13.53 s), two slots give ~1.45x at two clients (9.21 tokens/s) but only ~1.19x at four, and four slots cut single-client throughput to 3.32 tokens/s while raising server RSS to 6.09 GB and system RAM to 87.7%. Decision: keep one slot as the safe default; two slots are the opt-in maximum for concurrent serving; reject four. No linear-scaling or production multi-tenant claim.
- D-060 (EXP-020): `tony:7b-agentic3` is not promoted for tool use. On a frozen 12-item native Ollama tool-calling suite (sha256 `ed3a5345...`), agentic3 and `tony:7b-gpa3` both scored 11/12 on answer and agentic success (0 wins, 0 losses, 12 ties, p=1.000), with tool accuracy 1.00, clean 1.00 and recovery 1.00. Both failed the same `lookup-01` entity-to-key mapping and both fixed `2 ** 3 ** 2` with the calculator. Agentic3 was slower at p50 (6.33 s vs 5.84 s) and load (7.1 s vs 5.1 s). Keep gpa3 as the general/tool-use model; retain agentic3 only as an evaluated candidate. This is a bounded negative result, not a general agentic-capability estimate.
