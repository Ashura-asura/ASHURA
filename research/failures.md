# Failures and limitations found so far

**F-001 - AMA discard branch nearly unreachable at default weights.** Items >= 0.9 similar are merged before scoring; items below that have novelty >= ~0.1, and an unverified item then scores >= ~0.5, above the 0.45 threshold. Found when my "chatter is discarded" test failed. I did not retune the threshold to pass the test. Action: calibrate on realistic data (EXP-001 sweep is a start).

**F-002 - False conflicts on rewordings. FIXED (with limits), see below.** Same question + differently-worded but equivalent answer (Jaccard < 0.9) is treated as a contradiction: stored as evidence, not indexed, flagged for review. 63% of rewordings in EXP-001. Needs a semantic/number-aware comparison (e.g. compare extracted values) rather than token overlap.
  *Fix:* `learning/ama.py::answers_agree` - answer values (digit-bearing tokens not already in the question) must be identical, negation parity must match, and value-free answers must share >= 75% of their content words. EXP-001 rewording false-conflict rate 63.1% -> 0.0%; 8 adversarial contradictions (transposed digits, negation, hedged extra value, value-vs-none, different city/weekday) are all still caught (tests/test_ama.py). *Remaining limits:* number words vs digits ("four" vs 4), units ("5 km" vs "5 miles"), and paraphrases with no shared content words are NOT understood - they fall back to "disagree" (stored as evidence, never silently merged). The reworded test cases were again written by the same author.

**F-003 - Router RAM guard rejected the already-loaded model (fixed).** With ~4 GB free, the 2.5 GB language model failed the headroom check and nothing could answer. Fix: `resident` modules cost no additional RAM. Found by smoke test, then covered by `test_low_ram_...`.

**F-004 - AMA overhead.** Default AMA is ~5x slower per admission and the DB is larger than store-everything (EXP-001). Acceptable off the response path, but worth reducing before claiming "resource efficient".

**F-005 - Benchmark judge is substring-based and gameable** (see EXP-000). **FIXED:** `evaluation/judge.py` strips copied prompt text, matches whole tokens, and reports a strict score (first line / first word) beside the lenient one; the echo stub now scores 0% (was 18.75%). `baseline_v2.jsonl` fixes the "buenos d" prefix accept and marks yes/no items first-word. Residual: strict mode can under-credit models that think aloud before answering; the suite is still 16 items by one author.

**F-006 - Arithmetic verification is only independent for + - * / (PARTLY FIXED).** The Decimal(60) backend now also cross-checks `%`, integer `**` and perfect-square `sqrt`, so those results can become verified. Irrational roots (`sqrt(2)`), non-integer exponents (`2 ** 0.5`) and comparisons still have no independent check and stay unverified.

**F-007 - Adaptive memory has no demonstrated advantage over FTS5.** On lexical lookups FTS5 scored 1.000 everywhere; the neural memory ties only if capacity (dimension) is large relative to the number of facts, and degrades beyond it (EXP-004). Not a bug; a negative-leaning result that must stay visible. Need a semantic-generalisation task and a pretrained/learned encoder to find a case where it earns its place.

**F-008 - Raw hashed-token keys are nearly useless without IDF weighting** (shared template tokens dominate). Any future featuriser must handle common-token dominance.

**F-009 - Same-key conflicting updates** for the adaptive memory: **TESTED (EXP-005).** The neural memory has no reliability gate: the latest write wins at every lr/passes setting tried, so a wrong claim would overwrite a right one. Protection comes entirely from AMA, which never queues a weaker conflicting claim. Long-run interference over many updates is still untested.

**F-010 - Deleted experiences stayed searchable and quotable (FIXED).** `EpisodicMemory.delete` removed only the `experiences` row, leaving its FTS5 entry (still returned by search) AND any derived `facts` row (still quoted as reliable semantic memory). Violated the Phase 1 completion criterion "deleted correctly". Found by reviewing the code, reproduced before fixing. *Fix:* database triggers (`trg_exp_delete_facts`, `trg_exp_delete_fts`) so no path - including raw SQL - can bypass it; `delete()` now runs in one transaction, scrubs the id from other records' `related_ids`, and returns False for unknown ids; `EpisodicMemory.reconcile_index()` repairs databases written before the fix. `admission_log` is intentionally kept as an audit trail. 6 regression tests.

**F-011 - Router checked only RAM (FIXED) and used placeholder costs (PARTLY FIXED).** `NeedField` now defers optional, non-resident, heavy (>= 500 ms) modules when system CPU > 85%; the resident language model is never starved. `default_registry` reads `config/module_costs.json` (written by `ollama_baseline --calibrate`) for the language module; until that is run on the laptop the figures remain placeholders. Costs of non-language modules are still estimates.

**F-012 - AMA surprise was never computed (FIXED in Phase 2; proxy remains).** `surprise_from_prior` now uses a continuous `answer_similarity` over values, units, dates, content words and scoped negation, so a related mismatch produces an intermediate error instead of only 0/1 on exact-question matches. The Brier score is 0.013 vs 0.381 for the lexical baseline on 28 author-written pairs, but it is still prediction error against memory, not a calibrated probability against the language model.

**F-013 - Forgetting policy missing (FIXED).** `memory/retention.py`: only unverified, never-reinforced, unrelated, non-queued records older than `max_age_days` (or beyond an optional row cap) are forgotten; every removal is logged. The 30-day default and any cap are guesses, not tuned.

**Still open (not fixable without real data or hardware):** F-001/F-035 (AMA threshold/weights need a realistic stream that includes useful unverified items; the synthetic sweep is not a truth calibration), F-042 (natural-language claims and non-exact expressions still have no verifier), F-007/F-037 (adaptive memory still has no demonstrated advantage over FTS5; semantic generalisation needs a real encoder), F-036/F-038 (task-switch interference and replay ratios remain unsolved), F-008, and Phase 0 itself (the 16-item baseline is small). F-047 is fixed for explicit bounded concurrency; linear four-way scaling remains undemonstrated.

**F-004 - AMA admission cost and storage (FIXED in Phase 2, with an intentional remainder).** Admission is now one transaction with cached tokenisation: 1.40 ms/item vs 1.13 ms for store-everything on EXP-001 (1.24x, previously ~6x). The database is still ~27% larger because `admission_log` (~308 KB), semantic facts (~99 KB) and conflict evidence (~18 KB) are audit/derived state; semantic fact text is deduplicated when identical to its source episode. Do not remove the audit trail just to win a size benchmark.

**F-014 - The 7B foundation does not fit the target GPU (Phase 0).** `tony_control:7b` scored 0.94 strict but took **50.7 s p50** (90.3 s p95) on the MX350 because the 4.6 GB model exceeds 2 GB VRAM; generation itself was 7.3 tok/s, so most latency was memory movement/CPU fallback. A 7B-on-2 GB plan is not viable. Fix: pin `qwen3.5:2b` (2.3 GB, 4.5 s p50, 16.5 tok/s) as the live foundation; keep 7B only as an offline quality reference.

**F-015 - Qwen3.5-2B is weak at arithmetic (0.20 strict) and only 0.56 overall.** This is expected for 1.9B and is partially masked by routing: arithmetic prompts go to the exact path (smoke test answered 17*23 = 391 in 1.1 ms). It is still a real limitation for any question the router sends to the language model. The 16-item suite is too small to rank models precisely; do not over-read the 0.56.

**F-016 - OCR is implemented but not measured on the target corpus.** The optional local Tesseract adapter, correction store and CER/WER runner pass code-level tests, but no labelled target-document corpus has been run, so accuracy, latency and language coverage are unknown. Do not claim OCR capability from unit tests. Fix: build a held-out JSONL manifest of target scans and run `evaluation.ocr_benchmark` on the laptop.

**F-017 - The "neural" addition candidate is linear least squares, not a neural arithmetic circuit.** It matches exact addition 1.000 on held-out pairs in [-1000, 1000] because it fits a linear function, not because it learned arithmetic. It adds no capability over the exact evaluator. Keep it as a non-authoritative candidate only; a real HARN test needs a nonlinear/digit-level model and a held-out distribution where exact evaluation is not already perfect.

**F-018 - BrainSim B2 saturates and does not test recurrence.** The GRU and a parameter-matched fixed MLP both score 1.000 at every delay, including unseen delays 12-20; the MLP trains 6-16x faster. The task only needs cue copying, so the delay is irrelevant. This falsifies the planned recurrent-advantage hypothesis. Fix: B2b with variable-length cues, distractors that must be filtered, or a relational/delay-dependent query.

**F-019 - BrainSim B3 gating assumes the task ID is already known.** Task-scoped memory retains old-rule accuracy at 1.000 versus 0.104 for shared memory, but the experiment supplies the task ID and uses verified writes, so it bypasses the surprise/admission logic. It is isolation under a known boundary, not learned task identification or general interference control.

## Production-hardening pass (code review; every item below was reproduced before it was fixed)

**F-020 - The CLI crashed on large exact results (FIXED).** `what is 2^20000` raised `ValueError: Exceeds the limit (4300 digits)` from `str(int)` and killed the session. Results above 4000 digits are now printed in scientific notation with the digit count; the process-wide int-string limit is left untouched. A chain of multiplications is also size-checked (it previously bypassed the `**` guard), and deeply nested/NUL-containing input becomes an `ArithmeticError` instead of a traceback.

**F-021 - Dates and phone numbers were "computed" and stored as verified (FIXED).** `2026-11-05` was read as 2026-11-05 = 2010, injected as a known fact and admitted to memory at reliability 1.0. ISO dates, 4-digit-year slash dates and 3-3-4 phone numbers are no longer treated as arithmetic. Spaced forms (`2026 - 11 - 05`) and `100-50-25` still compute. The heuristic parser is still a heuristic.

**F-022 - Routing results depended on the machine's live CPU/RAM (FIXED).** Two OCR tests failed whenever the host was busy; the same load-based deferral could also silently skip OCR when the user had explicitly typed `/ocr`. `NeedField` accepts `ram_fn` (like `cpu_fn`) so tests are deterministic, and `Task.force` lets an explicit request bypass load-based deferral (never availability).

**F-023 - A configured empty `WorkingMemory` was discarded (FIXED).** `wm or WorkingMemory()` is falsy for an empty container (`__len__ == 0`), and `app.main` never passed the config values anyway, so `working_memory_slots/ttl_s` were ignored. Both fixed.

**F-024 - Stale retrieval cache (FIXED).** Facts told in a normal turn were invisible to a question cached before them for up to 10 minutes. Admitting new memory now invalidates cached retrievals for other questions (the current question's own entry is kept so repeats still hit the fast path).

**F-025 - A model-backend failure crashed the request and the error text was learned (FIXED).** `Controller.handle` now degrades (exact answer, else memory, else a clear message) and does not admit the error message into memory. Malformed/`{"error":..}` Ollama responses become `OllamaError`.

**F-026 - Conflict detection scanned the whole experiences table per admission (FIXED).** `find_by_input` loaded every row and normalised in Python. A normalised `input_norm` column with an index is used instead; existing databases are migrated and backfilled automatically. SQLite also gets a busy timeout so a competing writer waits instead of failing immediately.

**F-027 - `pip install -e .` did not work (FIXED).** setuptools refused the flat layout ("Multiple top-level packages"); `pyproject.toml` now lists the packages, ships `schema.sql`, and exposes an `ashura` command. The CLI also finds its config from any working directory.

**F-028 - Smaller robustness fixes.** Unknown `[foundation]` keys give a clear error instead of a `TypeError`; checkpoint names cannot contain path separators; `promote()` copies atomically and refuses to overwrite a *different* stable file; a corrupt manifest gives a readable error; `new_ratio <= 0` no longer reaches a division by zero; the neural addition candidate is cached instead of re-read from disk per request and declines integers above 2**53 (float64 limit; huge ints raised `OverflowError`); adaptive-memory checkpoints are written atomically to the exact path requested (numpy silently appended `.npz`) and refuse to load with a different seed; OCR has a Tesseract timeout; `--calibrate` with a model that isn't being run now fails before the benchmark instead of after it; the benchmark continues past one failing non-reference model; the `[retention]` config section is now honoured by `python -m memory.retention`; the OCR test no longer hard-codes a Windows font path.

**F-029 - Unverified memory was retrieved as evidence (FIXED in Phase 1).** Retrieved memory was fed to the language model as `Memory:` context regardless of reliability, and the model's own *unverified* answers were admitted into that same memory. A wrong answer could therefore come back later as "memory". `AMA.retrieve()` now filters below `retrieval_min_reliability` (0.5) by default and labels every returned item with its provenance (`verified fact`, `user-provided, not independently verified`, etc.). Unverified records remain auditable in the database and can be inspected with `include_unverified=True`, but they are not presented as established memory. Semantic facts and DREAM labels now require `verification_status="verified"`, not merely a high reliability score. See D-027 and `research/phase1_trust.md`.

**F-030 - The benchmark reference was an unpinned, disappearing tag (PARTLY FIXED).** `ref-base:7b` was no longer installed and `tony_control:7b` had been deleted, so the old baseline could not be rerun. The default reference is now `tony:7b`, and every result row records a digest, but the tag still resolves to whichever build is installed. `tony:7b` (`0455603ff430`) is a different artifact from `tony_control:7b` (`c20c7b08841f`): it scored the same 0.94 strict but 2.35 s p50 instead of 50.7 s, so the F-014 latency claim must stay scoped to the old artifact. The 4.6 GB footprint still exceeds the 2 GB VRAM budget. Separately, `lfm3:latest` (same digest) scored 0.125 and 0.562 on different runs because its first run returned empty responses; thinking-model output is not reproducible until `think`/`num_predict` is pinned. Fix: record digests in reports, pass `--think` explicitly, and treat reference-tag changes as a new experiment.

**F-031 - Natural-language user corrections are not independently verified (OPEN, Phase 3).** A correction is now stored as its own `user_provided` record at reliability 0.6, which is honest about its source but still does not establish truth. It cannot enter semantic memory or DREAM, and it does not override verified (1.0) or trusted (0.8) evidence. The path that would turn a verified correction into a candidate update - CAGE attribution -> bounded proposal -> candidate training -> NGR - is implemented only at the gate/consumer level, not wired into the live controller. Do not describe a user-stored correction as learned truth.

**F-032 - A missing NGR performance requirement is still a policy choice (OPEN).** NGR now rejects missing or invalid p95/RAM measurements *when* `require_performance=True`, and sample counts when `require_sample_counts=True`, but both default to off for backward compatibility with the historical experiments. A promotion path that claims resource safety must enable them explicitly. Likewise, the score range default is [0, 1]; a capability measured on another scale must declare a `MetricSpec`.

**F-033 - DREAM's replay advantage is not established by EXP-006 (OPEN/negative).** With stable initialization, both stable+new and stable+replay retained old capability at 1.00 and learned the new capability at 1.00; replay added cost without a measurable benefit on this synthetic task. Fresh+new was rejected at 0.00 old retention, and fresh+replay passed. The honest conclusion is that the gate rejects forgetting and that stable initialization is a viable arm; it is not evidence that replay is the best consolidation method in general. The task is small, single-seed, author-written, and all facts fit the memory capacity.

**F-034 - Conflicting evidence is auditable but not searchable (FIXED in Phase 2).** A weaker conflicting record was retained in `experiences` but left out of the FTS index with no reviewer query. P21 now records every conflict in a dedicated `conflicts` table (question, both ids, statuses, reliability snapshots, policy, resolution, timestamps). `AMA.conflicts()` lists open conflicts and `resolve_conflict()` records an explicit resolution; supersession requires an independently verified experience. The remaining gap is workflow/UI, not the data model.

**F-035 - AMA threshold calibration is synthetic and the default was deliberately not changed (OPEN).** On 3 author-written seeds, precision at the default 0.45 is 0.35; at 1.6 it is 1.00. But 1.6 discards all novel unverified experiences, which the design keeps for audit and later review. The calibration also uses short templated records. Do not present 0.45 or 1.6 as a truth-calibrated threshold; re-measure on real traffic before changing the default.

**F-036 - Adaptive memory still suffers catastrophic task-switch interference (OPEN).** In the ~2,100-write long run, old-task accuracy fell from 0.84 to 0.04 after two switches and recovered to ~0.90 only after retraining on the old task. The neural-memory queue gate prevents unverified/conflicting writes, but it does not solve continual learning. Keep the memory experimental and task-scoped (D-035).

**F-037 - The adaptive memory has no measured advantage over FTS5 (OPEN/negative).** With IDF it reaches 0.997 exact on 100 synthetic facts, but FTS5 is 1.00; under 10 distractor tokens adaptive recall is 0.41 vs FTS5 1.00, and related recall at 400 facts is 0.88 vs 1.00. The result supports IDF, not adoption. Do not integrate the neural memory into the response path.

**F-038 - Replay ratios and sampling policies are not calibrated (OPEN).** All ratios (0.25/0.5/0.75/1.0) and both random/recent policies scored 1.00 new / 1.00 old retention on the EXP-006 buffer. The task is too small to distinguish them. The 0.5 default is a placeholder, not a measured optimum.

**F-039 - Conflict review is a minimal CLI, not a production workflow (PARTLY FIXED).** `learning/review.py list` surfaces open/all conflicts and `resolve` records an explicit reason; superseding still requires an independently verified experience. There is no UI, notification or queue prioritisation, so an open conflict can still go unseen, and the older record stays searchable while it is open. Safe, but incomplete for production audit.

**F-040 - Semantic provenance cannot establish that a fact is true (OPEN by design).** A semantic fact now requires a verified source experience and preserves provenance/derivation, but 'verified' still means an independent check within ASHURA's verifier coverage (for example exact arithmetic or passing tests). No general natural-language fact verifier exists, so most user statements remain `user_provided` or `trusted_material` and never become semantic facts.

**F-041 - Controller-side trace retention and an optional loop hook are implemented (FIXED at controller level).** `Controller` retains the last non-correction `ExecutionTrace` and, when a `correction_loop` hook is supplied, invokes it on a verified correction. Hook failures are captured in `Response.correction` instead of breaking the reply. `LearningWorker` (P67) can run the hook on a daemon thread and returns a `job_id`; queue-full, cancellation, error capture and controller integration are tested. The default CLI still does not configure a loop because it has no replay corpus or stable checkpoint, so a live session does not learn automatically.

**F-042 - Natural-language corrections remain unverifiable; arithmetic coverage is still bounded (PARTLY FIXED, P47).** `%`, integer powers and perfect-square roots are now independently checked as well. Factual claims, irrational roots, non-integer powers and arbitrary prose stay `user_provided`; the parser refuses to mark an unchecked claim verified.

**F-043 - The loop trains the adaptive memory, not the language model (OPEN by design).** The promoted candidate is a NumPy associative memory. ASHURA trains neither `tony:7b-gpa3` nor `tony:7b`; no adapter or LoRA is trained. EXP-018 evaluates the user-supplied checkpoints and selects gpa3 as the general tutor and tony:7b as the privacy profile, but that is model selection, not learning. EXP-017 shows that the NumPy candidate persists across a fresh process and retains the old capability; that is evidence for the NumPy consolidation mechanism, not for language-model learning. Do not describe EXP-013/EXP-017/EXP-018 as model self-improvement.

**F-044 - Correction benchmarks are still author-written and small (PARTLY FIXED).** EXP-013 (five seeds, one expression, two wordings) promoted 4/5 and rejected the fifth because the stable memory accidentally scored 1.00 on the corrected held-out items. EXP-014 expands this to 10 arithmetic forms, 3 held-out wordings each and 5 seeds: 50/50 replay runs promoted, 50/50 no-replay runs rejected, 150/150 held-out wording predictions correct and 25/25 control probes refused. The result is stable on the frozen set, but the corpus is still author-written, the held-out wordings share the expression tokens with the correction key, and there is no independent distribution. Keep both experiments as control-flow/non-regression evidence, not a capability estimate.

**F-045 - The background worker is in-process and non-durable (FIXED, BOUNDED).** `LearningWorker` now has a SQLite job store that persists payload, status, attempts and result; a fresh worker re-schedules queued jobs and marks previously running jobs interrupted; `hard_timeout_s` runs a job in a spawned child and terminates it at the deadline, returning stateful-runner updates when the callable is picklable. A real killed-process test and a timeout test cover both paths, and the CLI wiring is opt-in. Residual limits: one worker per store, at-least-once recovery for queued jobs, no multi-worker scheduling, and no live real-model learning run. This is bounded production-readiness evidence, not a claim of exactly-once execution.

**F-046 - Runtime scope was short, single-process and partly stub-based (FIXED, BOUNDED).** EXP-015 measured non-language costs, a 300-turn EchoModel mix and a short single-client `tony:7b` load. EXP-016 closes the bounded gap: four concurrent client processes completed 80 mixed turns with 0 failures; one forced unload/reload took 22.41 s wall (9.11 s Ollama load); a fresh ASHURA process (PID 12164 vs write PID 1552) found both a verified arithmetic record and a user-provided memory record; client RSS stayed <=97 MB and system RAM peaked at 83.9%. Scope is explicitly limited to client lifecycle, database persistence, model unload/reload and application restart. It is not production endurance, shared-database concurrency, thermal-throttling evidence or parallel throughput. The last point is F-047.

**F-047 - Concurrent clients queue on the local model instead of scaling (FIXED, BOUNDED).** EXP-016 ran four concurrent clients against the same local Ollama server. All 80 turns completed with 0 failures, but general-turn p50 rose from 5.52 s single-client (EXP-015) to 25.80 s (~4.7x), p95 was 35.23 s, and server CPU utilisation was only ~0.31. The observed behaviour was consistent with serialized/queued inference, not four-way parallel serving. EXP-019 now measures the server setting explicitly on `tony:7b-gpa3`: one slot serializes (4.93 to 5.95 tokens/s, p50 6.57 to 13.53 s across 1-4 clients); two slots give ~1.45x at two clients (9.21 tokens/s) but only ~1.19x at four (p95 22.4 s); four slots cut single-client throughput to 3.32 tokens/s, raise server-tree RSS to 6.09 GB and system RAM to 87.7%, and are rejected. The shipped profiles now bound the client side (`max_inflight=1`, `max_queue=8`, `queue_timeout_s=60`). Residual limits: no linear four-way scaling, no cross-process queue or multi-worker scheduler, and no production multi-tenant or thermal claim. Do not use the four-client p50 as a single-client latency estimate.
